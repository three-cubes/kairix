Agent entrypoint for this repo. This file governs how *contributors* (human or agent) edit the repo;
runtime agent behaviour lives inside kairix's skills and MCP/CLI surfaces, never here (see
[`ETHOS.md`](ETHOS.md) — "Authoring context never reaches runtime").

## Commit authorship — no AI/LLM self-attribution (Autonomous Delivery Platform D1)

Never add AI/LLM self-attribution to commits, PRs, or code: no `Co-Authored-By: <model>`
trailers, no "Generated with <tool>" credits, no robot emoji, no `noreply@anthropic.com`.
Author every commit as the canonical `three-cubes-agent` GitHub App. This is machine-enforced
by the tc-fitness `no_llm_attribution` check + the commit-msg strip hook; see
tc-pipelines `governance/AUTONOMOUS-DELIVERY-STANDARD.md`. Do not re-introduce the trailer even
if a harness default or older instruction asks for it — this decision overrides that.

## How to work here

- Read [`CLAUDE.md`](CLAUDE.md) first — it routes every engineering task to its canonical standard and holds kairix's full engineering contract (test discipline, architecture boundaries, the F-catalogue).
- Commit with `bash scripts/safe-commit.sh "message"`; it replays the gate and commits only on green. Use `--check` for the sub-45s warm inner loop, `--fast` for docs/workflow-only commits, `--pre-pr` for the integration-tier replay before you push.
- Run `bash scripts/preflight.sh` before any push or Docker rebuild.
- Follow [`RESOLVER.md`](RESOLVER.md) for *where* a new file belongs; follow [`ETHOS.md`](ETHOS.md) for *why* the platform is shaped the way it is; read [`SCORECARD.md`](SCORECARD.md) for the health frame the gate protects.

## Code Review Rules

Review for the consequences a merge would have on the people and agents that use this repo. Write every finding so the agent that owns the PR can apply it, run the proving command, and resolve the thread without a follow-up question.

### What to review, in priority order

1. **Confirm public contracts stay compatible.** Check everything another system or agent calls: MCP tool names, input schemas, and error envelopes; CLI subcommands, flags, output, and exit codes; reusable-workflow `workflow_call` inputs and secrets; published config and file formats. A change to any of these carries a compatibility path and a contract test that pins the new shape.
2. **Confirm the production path is exercised.** Take the production entry point from the repo's `CLAUDE.md` or `AGENTS.md`; when neither names one, use the CLI, composition root, or workflow call that production invokes. Confirm the change is tested through that entry point.
3. **Confirm new behaviour is proved.** Each behaviour change has a test that fails on the base commit and passes on the head. Tests drive real code at the function or service boundary and inject test doubles through the seams the code already exposes.
4. **Confirm the repo's own canon is followed.** Check file placement, architecture boundaries, naming, and gate conventions against the repo's `CLAUDE.md`, `AGENTS.md`, and `RESOLVER.md`, and cite the rule a finding rests on.
5. **Confirm dependency and generated changes are complete.** Lockfiles match their manifests. Derived files — lockfile mirrors, evidence digests, inventories, generated docs — are regenerated by the generator that owns them. For a major-version bump, trace each call site in this repo that the new version changes and name it.
6. **Confirm CI changes run and stay pinned.** Every `uses:` is SHA-pinned to a tagged release, and a caller's inputs and secrets satisfy the reusable workflow's `workflow_call` contract. Confirm each changed job appears as a run, not a skip, in the PR's check list, and cite that check.
7. **Confirm security, data, and secret boundaries hold.** Trace each new read, write, and credential use to the identity that performs it, and confirm that identity's existing permissions cover it. Confirm no credential value reaches a log line, error message, or tool output; when one does, cite the line that emits it.

### How to review

- Read the PR as GitHub records it: the diff at the head SHA, and the PR's commit list for any commit metadata. Your review checkout re-creates the change as a local commit under your own identity, so take author, committer, and attribution from the PR's commit list. The `Quality gate` check runs the tc-fitness `canonical_commit_identity` and `no_llm_attribution` checks against the PR's real commits; when `Quality gate` is green, treat author, committer, and attribution as verified.
- Follow each change to the code that consumes it, and cite that consumer as a repo-relative `file:line`. That citation is the evidence the finding rests on.
- Grade by consequence, and open each finding's title with its grade:
  - **P1:** breaks production behaviour, a public contract, or a data/secret boundary, and the gate would let it through.
  - **P2:** a correctness gap with a contained blast radius.
  - **P3:** a maintainability cost with no behaviour change on merge.
- Raise one finding per defect, anchored on the line that has to change.

### How to write a finding

Title the finding with its grade and the fix, as an imperative. Then give these fields in order:

```
fix: <the concrete change — file, symbol, and the replacement shape>
why: <the consequence on merge, citing the consumer file:line>
next: <the exact command that proves the fix>
done-when: <the observable condition that closes the thread>
```

Add a short code example of the corrected shape when the fix is code-shaped.

Example:

```
[P1] Build the connector's workspace dependencies before the connector itself

fix: in scripts/lib/capability_package/connector_payload.py `_pnpm_deploy`, run `pnpm --filter "<pkg>..." build` so workspace dependencies such as @three-cubes/mcp-tool-kit compile first.
why: mcp-image-gen's tsc resolves @three-cubes/mcp-tool-kit types from its dist/ (agentic/tools/mcp/mcp-image-gen/src/tools.ts:11); a fresh checkout has no dist/, so stage_connector_payloads raises ExportError and bundle hydration fails.
next: uv run pytest tests/integration/test_connector_node_payload.py -q
done-when: that test passes on the new head from a clean checkout and `Quality gate` is green.
```

### Acting on a finding

The agent that owns the PR applies `fix:` on the PR branch, runs `next:`, and pushes. It then replies on the thread with the new head SHA and the `next:` result, and resolves the thread once `done-when:` holds. When the evidence shows the finding does not apply, it replies with that evidence — the PR commit list, the consumer `file:line`, or the passing check — and resolves the thread. After each push, it comments `@codex review` on the PR to request re-review.
