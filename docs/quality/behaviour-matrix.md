# Behaviour Traceability Matrix

This document pins every user-observable kairix capability to the tests that prove it.
One row per capability (CLI subcommand + flag combo, MCP tool + input variant, or
connector write to read round-trip). One column per test layer (Contract, Unit,
Integration, BDD, E2E). Each cell is either a `<test_path>::<test_fn>` pin, an explicit
`MISSING: <reason>` gap, or an explicit `EXEMPT: <reason>` carve-out — never blank.

The matrix is the structural record of what is and is not pinned to a behavioural
assertion. Line coverage measures whether code ran. The matrix measures whether the
behaviour was checked.

## How to use this doc

**Reading a row.** Pick the capability you are about to touch. If every cell is a
`<test_path>::<test_fn>` pin, the behaviour is covered at every layer — you can refactor
with confidence. If a cell is `MISSING:`, the rationale tells you what regression class
is unguarded; if it is `EXEMPT:`, the rationale tells you why no test is owed.

**Cell shapes.**

- `<test_path>::<test_fn>` — pin. The named test asserts on observable output (stdout
  envelope, returned dict, persisted state) for this capability at this layer. The
  test path is repo-relative, the test function is the assertion that pins the
  behaviour. Per F30, the assertion must be on content (stdout/stderr/envelope), not
  on `returncode == 0` alone.
- `MISSING: <reason>` — gap. The capability is shipping today, but no test pins this
  layer's contract. The reason names the regression class that gap risks (the IM-6
  CLI flag and FTS write gaps are the canonical examples). Phase 2 paydown work
  converts `MISSING:` cells into pins.
- `EXEMPT: <reason>` — carve-out. The capability genuinely does not owe a test at this
  layer (e.g. diagnostic-only command with no behavioural contract, MCP-only tool with
  no CLI mirror, contract-layer N/A for a connector round-trip that is integration-only
  by design). The reason names why.

**Discipline.**

- New CLI subcommands (additions to `kairix.cli.COMMANDS`), new `@server.tool()` MCP
  tools, and new connector/extractor/provider plugins land with a matrix row in the
  same commit. Phase 2's F62 detector blocks otherwise.
- New writer/reader round-trip pairs land with an integration test in the same commit
  and a row in this matrix. Phase 2's F63 detector blocks otherwise.
- Per-release gate (Phase 2): the `MISSING:` cell count must monotonically decrease
  per release tag, or stay at zero.

**What this matrix prevents.** The IM-6 cutover (2026-05-23) shipped two regressions
that line-coverage tools and existing fitness functions missed:

1. `kairix search --collection X` raised `TypeError` because `_default_search()` did
   not accept the `collections` kwarg. F30 outcome tests existed for `kairix search`,
   but they exercised only the no-flag invocation; the `--collection` variant was
   unpinned.
2. `_SqliteChunkWriter.upsert` wrote to `documents` but skipped `documents_fts`. Unit
   tests covered the DB write; integration tests covered FTS query; no test asserted
   the round-trip `after upsert, BM25 finds it`. The gap lived between two
   well-tested layers.

Both failure modes show up immediately as `MISSING:` cells in the matrix below. That
is the value — coverage of behaviours is the contract, not coverage of lines.
